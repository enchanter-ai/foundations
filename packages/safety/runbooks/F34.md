# F34 — Untrusted-context injection

Failure code from `taxonomy/f34-untrusted-context-injection.md`.

## Signature
A model treated content that entered context through a data channel — file body, tool result, retrieved document, inbound ticket/email, MCP response — as an instruction from the principal, and acted on it. Indirect prompt injection: the principal never typed the directive; it rode in on data the agent was processing.

## Detection
- **Audit-trail signal:** a state-changing or tool-invoking action whose only justification traces to untrusted-channel content — the requested action appears in a tool result or retrieved document but nowhere in the principal's actual instruction.
- **Provenance signal:** content acted upon was not wrapped `<untrusted_source>` on ingestion, or the wrap was present but an imperative inside it was executed rather than surfaced.
- **Self-report signal:** the agent's rationale cites "the document says to…" or "the file instructs…" for an action the principal did not request.

## Triage
1. Identify the action taken and trace its justification back to the originating content.
2. Determine the channel (file / tool result / retrieval / inbound item / MCP) and whether that channel was provenance-marked on ingestion.
3. Assess impact: was the action reversible? Did it exfiltrate data, change state, or escalate tool scope? (If a harmful operation resulted, F21 co-fires; if destructive without confirmation, F10 co-fires.)

## Rollback
- **If during a skill run:** halt the agent; revert any state change the injected directive caused; re-process the source content as data only, surfacing the embedded directive to the principal rather than acting on it.
- **If during a deployed plugin:** disable the affected path; confirm the ingestion layer wraps every data channel as untrusted before re-enabling.
- **State to verify before resuming:** every data channel is wrapped on ingestion; security-critical refusal (no exfiltration, no tool-scope escalation, no state change sourced solely from untrusted content) is enforced by the host runtime, not by a prompt-level rule; sensitive actions are gated by provenance-displaying confirmation.

## Post-incident
- Log the incident in the relevant plugin's `state/precedent-log.md` with the channel, the injected directive, and the impact.
- If the failure was missed by an existing detector, file an issue under `vis/runbooks/improvements/`.
- If 3+ instances in one workflow, the instruction/data boundary is not enforced at the host — stop relying on prompt-level refusal and audit the runtime per `skills/recipes/agent-runtime-boundaries.md`.
